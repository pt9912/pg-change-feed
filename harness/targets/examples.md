# `make examples-*` und `make example-*` — Beispiel-Clients bauen und starten

Ausführliche Fassung der Index-Zeilen aus [`harness/README.md` §Sensors](../README.md#sensors-feedback-gates); die Zeile dort trägt einen Satz und verlinkt hierher.

## `make examples-csharp`

baut die vier Werkzeugketten-Images der C#-Sprach-Wurzel (Bau-Kontext `examples/csharp/`, eigenes digest-gepinntes Dockerfile, gemeinsame `build`-Stufe) — `pg-change-feed-examples:csharp` (http-client), `pg-change-feed-examples:csharp-sse` (sse-client), `pg-change-feed-examples:csharp-nats` (nats-client) und `pg-change-feed-examples:csharp-grpc` (grpc-client, seit slice-102) — und fährt darin `dotnet restore`/`build`/`test` für alle vier Programme; ein roter Test bricht den `docker build` ab; die Beispiele bleiben Doku mit Bau-Bindung, kein Lauf-Beleg. Für grpc-client liest der Bau die `.proto` zusätzlich über einen benannten Bau-Kontext (`--build-context proto=proto`, `COPY --from=proto …`) — jeder der vier Aufrufe trägt ihn zwingend, ohne ihn bricht der Bau an dieser Stelle ab. Das gRPC-Programm wählt den Transport über `--ca-file`/`CDC_TLS_CA_FILE` (Vertrauensanker als PEM-Datei: TLS mit Prüfung von Kette und Name, ohne Angabe Klartext; `ChannelFactory.cs`, Tests `ChannelFactoryTests`). Braucht Netz (NuGet-Paketbezug), deshalb Werkzeug statt Gate

**Bindung:** kein Gate, [`ADR-0087`](../../docs/plan/adr/0087-beispiel-clients-csharp-kotlin.md), [`ADR-0090`](../../docs/plan/adr/0090-beispiel-clients-volle-matrix.md) · seit slice-098, erweitert seit slice-100, seit slice-101, seit slice-102

Für grpc-client liest der Bau die `.proto` zusätzlich über einen benannten Bau-Kontext (`--build-context proto=proto`, `COPY --from=proto …`) — jeder der vier Aufrufe trägt ihn zwingend, ohne ihn bricht der Bau an dieser Stelle ab. Braucht Netz (Maven-Central-/Gradle-Plugin-Portal-Paketbezug), deshalb Werkzeug statt Gate

## `make example-run-go`

baut bei Bedarf (Docker-Layer-Cache) und startet real eines der vier Go-Beispiele — Pflicht-Argument `SURFACE=http|sse|grpc|nats`, optional `ARGS="…"` für die Flag-Übersteuerung je Beispiel; ein fehlendes/unbekanntes `SURFACE` bricht mit `$(error …)` ab, bevor `docker build`/`docker run` läuft. Bau-Quelle ist `examples/Dockerfile` (Bau-Kontext Repo-Wurzel, isoliert über `examples/Dockerfile.dockerignore`, digest-gepinnte Basis wiederverwendet aus der Wurzel-`Dockerfile`); der Start ist `docker run --rm --network cdc-examples --env-file examples/.env <image-tag> $(ARGS)` — das Docker-Netzwerk `cdc-examples` und `examples/.env` legt `slice-beispiele-compose-bootstrap` an, dieses Ziel referenziert beide nur. Analog dazu, aber ohne eigenen Bau-Schritt: `example-run-csharp`/`example-run-kotlin` (siehe Zeile darunter). Das gRPC-Beispiel (`SURFACE=grpc`) verbindet über TLS, wenn `-ca-file`/`CDC_TLS_CA_FILE` einen Vertrauensanker nennt (`ARGS` trägt das Flag, die Datei muss im Container liegen; der Make-Aufruf mountet sie nicht, die Aufrufform steht im Benutzerhandbuch). Braucht das benannte Docker-Netzwerk, deshalb Werkzeug statt Gate

**Bindung:** kein Gate, [`ADR-0098`](../../docs/plan/adr/0098-beispiel-clients-start-ueber-make-dockerfile.md)

## `make example-run-csharp`/`make example-run-kotlin`

startet real eines der vier bereits gebauten C#- bzw. Kotlin-Beispiele — Pflicht-Argument `SURFACE=http|sse|grpc|nats`, optional `ARGS="…"` für die Flag-Übersteuerung je Beispiel; ein fehlendes/unbekanntes `SURFACE` bricht mit `$(error …)` ab, bevor `docker run` läuft. Anders als `example-run-go` bauen diese Ziele **nichts** — der Bau liegt bei `make examples-csharp`/`make examples-kotlin` (`ADR-0087`/`ADR-0090`, unverändert); der Start ist `docker run --rm --network cdc-examples --env-file examples/.env pg-change-feed-examples:csharp[-<surface>]`/`:kotlin[-<surface>] $(ARGS)` gegen den bereits vorhandenen Image-Tag — läuft der Bau-Schritt noch nicht, scheitert `docker run` real und sichtbar mit einem Docker-eigenen „image not found", kein stiller Vorab-Bau. Das Docker-Netzwerk `cdc-examples` und `examples/.env` legt `slice-beispiele-compose-bootstrap` an, dieses Ziel referenziert beide nur. Braucht das benannte Docker-Netzwerk, deshalb Werkzeug statt Gate

**Bindung:** kein Gate, [`ADR-0098`](../../docs/plan/adr/0098-beispiel-clients-start-ueber-make-dockerfile.md) · seit slice-beispiele-csharp-kotlin-start-target

## `make example-demo-up`/`make example-demo-down`

fährt die Demo-/Quickstart-Umgebung unter `examples/` real hoch bzw. räumt sie ab (`examples/compose.yaml`, eigenes Docker-Netzwerk `cdc-examples`, eigenständig von der Wurzel-`compose.yaml` — beide können gleichzeitig laufen, real geprüft): PostgreSQL+NATS starten, Schema-Rollout über d-migrate treiben (`tools/schema/apply-rollout.sh`-Muster, `examples/bootstrap.sh`), eine Beispiel-Quelle (`cdc.source`) und -Tabelle (`public.orders`, eine Demo-Zeile) registrieren, dann den Feed-Container starten — der aktiviert `public.orders` beim eigenen Start automatisch über `CDC_TABLES` (`ADR-0028`). Die Demo-Zeile wird erst **nach** Anlage des Replication-Slots eingefügt (logische Replikation trägt keinen initialen Snapshot-Export dieses Wegs — eine frühere Zeile bliebe über `GET /changes` unsichtbar, real geprüft); danach liefert `GET /changes?source=demo-source` real die Zeile, ohne dass ein Nutzer manuell SQL oder `make schema-rollout` aufruft. Idempotent: ein zweiter `example-demo-up`-Lauf überspringt den Rollout-Schritt gegen ein bereits migriertes Ziel über den eigenen, aufruferseitigen Existenz-Check von `examples/bootstrap.sh`; `make schema-rollout` selbst ist ebenfalls idempotent gegen die elf bekannten Fremdobjekte ([`harness/targets/schema-rollout.md`](schema-rollout.md)), der Aufrufer-Check besteht daneben. Fügt die Demo-Zeile nur ein, wenn `public.orders` noch leer ist. `examples/.env` (committet, keine Vorlage, `ADR-0098` Festlegung 3) ist die gemeinsame Umgebungsdatei-Quelle für den Feed-Container (`env_file:`) und jedes `make example-run-*`-Ziel (`--env-file`). Braucht DB-Zugang und das benannte Docker-Netzwerk, deshalb Werkzeug statt Gate

**Bindung:** kein Gate, [`ADR-0098`](../../docs/plan/adr/0098-beispiel-clients-start-ueber-make-dockerfile.md) · seit slice-beispiele-compose-bootstrap

## `make example-transformation-demo`

zeigt die Wirkung einer Transformationsregel live an der bereits laufenden Demo-Umgebung (`examples/transformation-demo.sh`): `cdc.set_transformation` benennt die Spalte `customer` von `public.orders` im Row Image auf `customer_name` um, Status-Poll auf `applied`, danach eine neue Zeile einfügen und Rohform (die von `examples/bootstrap.sh` eingefügte Demo-Zeile) gegen die transformierte Form (die neue Zeile) über `cdc.changes` gegenüberstellen. Braucht die laufende Demo-Umgebung (`make example-demo-up` zuvor), deshalb Werkzeug statt Gate

**Bindung:** kein Gate, [`ADR-0112`](../../docs/plan/adr/0112-transformationsform-deklarative-regeln-vor-persistenz.md)
